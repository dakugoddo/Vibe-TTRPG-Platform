# Codex Maxxing Workflow для Vibe TTRPG Platform

> Дата: 2026-05-19
> Основано на статье Jason Liu: https://jxnl.github.io/blog/writing/2026/05/10/codex-maxxing/

## Смысл

Идея не в одном "идеальном промпте". Идея в рабочем контуре:

- долговечная нить по проекту;
- память в файлах, которые можно читать, править и диффать;
- четкие цели с проверками;
- steering во время работы;
- браузер/side panel для визуального QA;
- heartbeats/автоматизации только там, где реально нужен повторный контроль.

Для этого проекта `.pi` является проектной памятью. Чат помогает работать, но важные решения должны попадать в `.pi`, иначе после compaction или новой сессии они потеряются.

## Что агент делает сам

Агент может:

- читать `AGENTS.md`, `.pi/DEVELOPMENT_PLAN.md`, `.pi/FEATURE_STATUS.md` и профильные `.pi/docs/*` перед работой;
- обновлять `.pi` после значимых решений, проверок и архитектурных развилок;
- делать кодовые изменения в проекте;
- запускать локальные проверки: lint, build, TypeScript, focused tests;
- создавать focused tests для фундамента;
- поддерживать список известных рисков и не прятать спорные моменты;
- вести работу итерационно: маленький срез -> проверка -> документация -> следующий срез;
- использовать Browser/side panel для визуальной проверки, если в текущей сессии доступен соответствующий инструмент.

## Что должен делать владелец проекта

Владелец проекта должен вручную:

- держать эту Codex-нить закрепленной как основной workstream проекта;
- давать решения по продуктовым и системным развилкам, где у агента нет полной игровой системы;
- подключать внешние Codex-коннекторы, если они понадобятся: Chrome, Slack, Gmail, Calendar, GitHub;
- разрешать доступы/эскалации, когда нужно выйти за sandbox или запустить внешний инструмент;
- задавать секреты и API-ключи, например будущий random.org key;
- проводить субъективную ручную проверку UX: удобно ли ГМу, понятно ли игроку, соответствует ли авторской системе;
- голосом или текстом докидывать steering, пока агент работает, если заметил неверный акцент.

## Как формулировать задачи

Хорошая задача:

```text
Цель: сделать выдачу предметов игрокам рабочей в доверенной multiplayer модели.
Критерий готовности: ГМ выдает копию предмета игроку, предмет виден в user inventory, исходный шаблон остается в general, build проходит.
Ограничения: не менять формат .md, не вводить новые зависимости.
Проверка: lint/build, focused test или ручной сценарий.
```

Плохая задача:

```text
Сделай инвентарь нормально.
```

Можно говорить неидеально и длинно. Лучше дать сырой контекст, чем короткую команду без причин. Но после обсуждения агент должен сам ужать это в проверяемый срез.

## Память проекта

Файлы памяти:

- `.pi/PRODUCT_VISION.md` - зачем существует проект;
- `.pi/ARCHITECTURE.md` - текущие архитектурные правила;
- `.pi/ARCHITECTURE_ANALYSIS.md` - риски и фундаментальные развилки;
- `.pi/DEVELOPMENT_PLAN.md` - маршрут разработки;
- `.pi/FEATURE_STATUS.md` - что уже работает;
- `.pi/docs/*` - детальные контракты.

Правило: если решение важно для будущей разработки, оно должно попасть в один из этих файлов.

## Visual QA

Для UI-задач нормальный контур такой:

1. Агент меняет код.
2. Агент запускает lint/build.
3. Если доступен Browser/side panel, агент открывает локальный app и проверяет интерфейс.
4. Если Browser/side panel недоступен, владелец запускает `start.bat` и проверяет `http://localhost:5173`.
5. Владелец дает steering: "это мелко", "это не туда", "кнопка нужна ближе", "проверил, работает".

## Heartbeats и автоматизации

Heartbeats нужны не для обычной разработки, а для повторных ожиданий:

- проверить через 30 минут, не появились ли ошибки в долгой сборке;
- напомнить продолжить ручной QA;
- мониторить внешний feedback loop;
- вернуться к задаче после паузы.

Без конкретного расписания и условия успеха heartbeat не создается.

## Connectors

Для текущей локальной разработки не нужны Slack/Gmail/Calendar. Потенциально полезны:

- GitHub - если проект будет вести PR/issues;
- Chrome или Browser - для визуальной проверки локального UI;
- Google Drive/Docs - если дизайн-документы переедут из `.pi` во внешние документы.

Коннекторы подключает владелец проекта. Агент может сказать, какой нужен и зачем.

## Текущий рабочий режим

Для Vibe TTRPG Platform используем такой режим:

1. Доверенная privacy модель: UI скрывает GM-only/user данные, без отдельного private sync.
2. Roll Engine остается единой точкой для бросков.
3. `.md` frontmatter и Obsidian-совместимость не ломаются.
4. После каждого значимого среза обновляется `.pi`.
5. Разработка идет через вертикальный сценарий: открыть мир -> canvas -> игрок -> броски -> раны -> выдача предметов -> gm-only -> портал -> сохранение.
