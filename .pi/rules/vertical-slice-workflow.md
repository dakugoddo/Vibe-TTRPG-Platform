# Правила планирования и вертикальных срезов

> Процедура работы. Актуальное состояние проекта здесь **не хранится**.

## Канонические источники

- `.pi/DEVELOPMENT_PLAN.md` — понятный владельцу текущий roadmap.
- `.pi/planning/IDEAS.md` — входящие идеи и критическая оценка.
- `.pi/planning/BUGS.md` — только активные дефекты и обязательная QA.
- `.pi/planning/QUESTIONS.md` — решения владельца.
- `.pi/planning/NEXT_RELEASE.md` — завершённое для следующего релиза.
- `.pi/docs/*.md` — подробные архитектурные и UX-контракты.
- `skills/product-planning-gate/SKILL.md` — как разбирать идеи до планирования.
- `skills/vertical-slice-planner/SKILL.md` — как дробить уже принятую работу.

Не дублировать полные записи между файлами. В roadmap используется короткая формулировка и ссылка на каноническую запись.

## 1. Новое сообщение владельца

Любой содержательный материал обрабатывается серьёзно:

- идея или референс;
- баг/неожиданное поведение;
- документ, видео, screenshot set, внешний URL;
- критика текущего продукта;
- просьба `продолжай`.

Но сообщение не всегда означает «сразу написать код».

### Idea/reference intake

1. Записать смысл в `IDEAS.md`.
2. Проверить существующее поведение, roadmap и docs.
3. Назвать пользовательскую проблему и затронутую роль.
4. Критически оценить пользу, дублирование, риски, стоимость и product fit.
5. Выбрать: принять, уточнить, отложить, объединить или отклонить.
6. При важной развилке создать вопрос в `QUESTIONS.md` и спросить владельца.
7. Только принятую идею превратить в этап/срез roadmap.

Если материал большой, сначала добавить отдельную задачу анализа: что будет просмотрено, какие решения должны появиться и как проверить полноту обработки.

### Bug intake

1. Определить ожидаемое и фактическое поведение; при неоднозначности спросить.
2. Проверить, это дефект, missing feature или misunderstanding.
3. Записать в `BUGS.md`, назначить приоритет и понятный сценарий проверки.
4. `P0/P1` и баг текущего рабочего модуля исправлять раньше обычного roadmap.
5. `P2/P3` группировать по пользовательскому сценарию, чтобы не делать десятки разрозненных фиксов.
6. Agent-induced regression должен также улучшить профильный skill/rule/doc и focused regression check.

## 2. Когда вопрос владельцу обязателен

Остановиться до необратимой реализации, если выбор затрагивает:

- основной workflow или постоянное место функции в UI;
- `.md`/world file format, Yjs/sync, permissions/privacy/identity;
- plugin/mod API, платформу, Electron lifecycle, внешний сервис;
- новую dependency;
- миграцию или риск потери данных;
- два жизнеспособных UX/design варианта с разным пользовательским результатом;
- конфликт с ранее утверждённым решением.

Формат вопроса:

- почему решение нужно сейчас;
- 2–4 варианта в пользовательских терминах;
- рекомендация агента;
- последствия каждого варианта;
- какую обратимую работу можно делать до ответа.

Не спрашивать о мелких implementation details, которые не меняют продукт и безопасно выводятся из существующих контрактов.

## 3. Roadmap entry

Каждый активный срез в `DEVELOPMENT_PLAN.md` отвечает на шесть вопросов:

1. **Результат для пользователя** — что станет видно или возможно.
2. **Почему сейчас** — какую проблему/зависимость закрывает.
3. **Что сделаем** — 2–5 шагов простым языком.
4. **Не входит** — защита от разрастания.
5. **Готово, когда** — наблюдаемые критерии.
6. **Риски/решения** — ссылки на `BUGS.md`, `QUESTIONS.md`, design-doc.

Roadmap не должен быть отчётом по файлам, API и commit SHA. Технический execution plan при необходимости живёт отдельно и временно.

## 4. Вертикальный срез

Срез — минимальный production-инкремент через необходимые слои:

`world data / server / sync / state / UI / checks / docs`

Не каждый срез обязан менять все слои. Он обязан дать реальное пользовательское поведение или устранить конкретный риск.

Порядок:

1. Уточнить acceptance criteria и non-goals.
2. Проверить architecture/product gates.
3. Для behavior change начать с focused RED regression test, когда это практично.
4. Реализовать минимальный GREEN path.
5. Проверить errors, cleanup, permissions, sync, persistence, themes/density и backward compatibility по релевантности.
6. Выполнить focused tests, targeted lint/build и один пропорциональный реальный smoke.
7. Провести self-critique и independent review для рискованных/staged изменений.
8. Обновить planning vault и docs.
9. Зафиксировать отдельным осмысленным commit.

Не ограничивать работу искусственным количеством файлов или строк. Ограничение — единая понятная цель, обозримый риск и проверяемый результат.

## 5. Product/architecture gate

До реализации нужен design-doc и решение владельца, если затрагиваются:

- global UI/workflow;
- Entity/Markdown/world storage contract;
- Yjs/session sync и multiplayer authority;
- permissions/privacy/player identity;
- module/plugin/mod architecture;
- external API/service/dependency;
- native windows, Steam, 3D или другой платформенный фундамент.

До решения допустимы research, options analysis, tests и обратимый foundation, который не фиксирует спорную развилку.

## 6. Команда `продолжай`

`продолжай` означает автономно продолжить ближайший **уже принятый безопасный** срез.

- Не пересказывать roadmap вместо действий.
- Не останавливать работу из-за некритичных implementation choices.
- Не использовать `продолжай` как разрешение угадать product/architecture fork.
- При реальном gate записать вопрос в `QUESTIONS.md` и спросить владельца.
- Git/network/tooling blocker фиксировать явно; если безопасная работа возможна, продолжать её.

## 7. Завершение и changelog

Срез или баг завершён, когда критерии пройдены. Если обязательная owner/manual QA ещё не сделана, статус остаётся активным.

После завершения:

1. Удалить запись из активного roadmap/`BUGS.md`.
2. Добавить пользовательскую запись в `NEXT_RELEASE.md`.
3. Незавершённый follow-up оформить отдельной активной записью, а не оставлять скрытым в changelog.
4. Технический урок сохранить в профильном skill/rule/doc.
5. Обновить detailed design-doc только если изменился контракт.

Категории changelog:

- `Добавлено` — новая возможность.
- `Изменено` — заметно улучшенное поведение.
- `Исправлено` — устранённый дефект.
- `Безопасность` — authority/privacy/data-safety.
- `Документация` — важное изменение пользовательских/проектных правил.

При GitHub release содержимое переносится в версионный changelog/README RU+EN, затем `NEXT_RELEASE.md` очищается под следующую версию.

## 8. Git и проверка

- Один commit = один законченный product/fix/docs slice.
- Не коммитить непроверенное.
- Не смешивать runtime world/test data, generated output и unrelated changes.
- В shared dirty tree staging проверять по index, а не по всему working tree.
- Independent review относится только к точному staged fingerprint; любое staged изменение делает verdict устаревшим.
- Manual QA pending допустимо после automated checks, но запись остаётся активной и явно помеченной.

## 9. Коммуникация с владельцем

План и отчёт писать по-русски, для продвинутого непрограммиста:

- что изменится/изменилось в поведении;
- почему это важно;
- как доказано;
- что осталось;
- какие решения действительно нужны от владельца.

Не начинать с перечня файлов и не маскировать product tradeoff техническими терминами.
