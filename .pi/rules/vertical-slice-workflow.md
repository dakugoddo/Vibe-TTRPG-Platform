# 🍰 Vertical Slice Workflow

> Как мы работаем в vibe-стиле. От вайба — до кода.

---

## 1. ФИЛОСОФИЯ

**Vibe Coding** = итеративная разработка полными вертикальными срезами.

Вместо «сделаем всю БД, потом весь бекенд, потом весь фронтенд» — делаем одну фичу **сразу через все слои**:
```
DB → API → Store → UI/Canvas → Tests → Docs
```

Почему:
- Каждый слайс — демонстрируемый результат
- Риск блокировки минимален (никакой слой не ждёт другой)
- Быстрая обратная связь (видно сразу)
- Легко менять направление

## 2. ЦИКЛ РАБОТЫ

```
┌──────────────────────────────────────────────────┐
│  1. ВАЙБ  — Что хотим? Какая фича?             │
│      ↓                                           │
│  2. PRD   — Mini-PRD (полстраницы)              │
│      ↓                                           │
│  3. ПЛАН  — Вертикальные слайсы                │
│      ↓                                           │
│  4. КОД   — Итеративная реализация              │
│      ↓                                           │
│  5. КРИТИКА — Self-critique, edge cases         │
│      ↓                                           │
│  6. ТЕСТЫ — Модульные + интеграционные          │
│      ↓                                           │
│  7. ДОКИ  — .pi/docs/фича.md                   │
│      ↓                                           │
│  8. COMMIT — зафиксировать проверенный срез      │
└──────────────────────────────────────────────────┘
```

### Команда "Продолжай"

Когда владелец проекта пишет `продолжай`, это не вопрос и не просьба пересказать план. Это команда на автономную разработку.

Правило:

1. Продолжать работу по текущему roadmap и ближайшим безопасным срезам.
2. Не останавливаться на некритичных вопросах; записывать их и группировать для будущего обсуждения.
3. Сначала закрывать foundation-first задачи: данные, контракты, проверки, sync/permissions, потом UI-полировка и расширение.
4. Если git/commit/push/GitHub временно не работает из-за лимитов, sandbox, сети или авторизации, не превращать это в стопор. Зафиксировать факт и продолжать разработку с проверками.
5. Остановиться и спросить только при реальном блокере: риск потери данных, смена архитектурного фундамента, неоднозначная продуктовая развилка, требование новой зависимости или операция с повышенным риском.
6. В конце длинного прохода сообщить, что сделано, какие проверки прошли, что осталось на ручной QA и какие вопросы накопились.

## 3. ШАГ 1: ВАЙБ (Vibe)

Формат: свободный текст. Что хотим, какую проблему решаем.

```
Пример:
"Хочу, чтобы ГМ мог выдавать предметы игрокам drag&drop из общей базы в их инвентарь.
Сейчас предметы можно только вручную создавать в user-базе."
```

### Уточняющие вопросы:
- Кто пользователь? (ГМ, игрок, все)
- Где в UI это происходит?
- Какие ограничения? (только определённые типы? только между базами?)
- Что будет если ошибка? (предмет исчез? дубликат?)

## 4. ШАГ 2: MINI-PRD

Шаблон (полстраницы, не больше):

```markdown
# Mini-PRD: [Название фичи]

## Проблема
[1-2 предложения]

## Решение
[2-3 предложения]

## User Story
- Как [роль], я хочу [действие], чтобы [ценность]

## Acceptance Criteria
- [ ] Критерий 1
- [ ] Критерий 2
- [ ] Критерий 3

## Edge Cases
- Случай 1: [описание] → [ожидаемое поведение]
- Случай 2: [описание] → [ожидаемое поведение]

## Технические заметки
- Затрагивает файлы: [список]
- Новые зависимости: [нет / список]
- Риски: [список]
```

## 5. ШАГ 3: ПЛАН ВЕРТИКАЛЬНЫМИ СЛАЙСАМИ

```markdown
## Вертикальные слайсы

### Слайс 1: [название] (end-to-end проход)
- DB: [что в .md / что в Yjs]
- Server: [новые endpoint'ы]
- Store: [новые/изменяемые Zustand сторы]
- UI: [компоненты]
- Math: [если нужны вычисления]
- Tests: [что тестируем]

### Слайс 2: [название]
...
```

### Принципы слайсов:
1. Каждый слайс — **работающий** инкремент (можно показать)
2. Слайс 1 — самый тонкий (MVP фичи)
3. Слайс 2+ — дополнения, полировка, edge cases
4. Если слайс > 200 строк кода — разбей на под-слайсы

---

## 6. ШАГ 4: КОД (Итеративно)

### Порядок в каждом слайсе:
1. **Типы** — обнови интерфейсы
2. **Стор/Сервер** — данные и логика
3. **UI** — компоненты
4. **Стили** — Tailwind через theme.ts
5. **Интеграция** — соедини с существующим

### Правила генерации:
- Показывай код файла целиком (write) или diff (edit)
- После каждого файла — краткий комментарий что изменилось
- Не генерируй >3 файлов за раз без подтверждения

---

## 7. ШАГ 5: SELF-CRITIQUE

После каждого слайса — проверь:

### Чеклист
```
☐ Работает happy path
☐ Обработаны error states
☐ Нет утечек памяти (useEffect cleanup)
☐ Нет лишних ререндеров (useMemo/useCallback где надо)
☐ Совместимость с canvas (координаты, слои)
☐ Совместимость с Obsidian (.md формат)
☐ Мультиплеер (Yjs синхронизация не сломана)
☐ Права доступа (игрок не может то, что может только ГМ)
☐ Z-index не сломан
☐ Стили используют theme.ts (не хардкод)
```

### Edge Cases (TTRPG-специфичные):
```
☐ Что если стат не найден? (context bubbling)
☐ Что если сущность удалена во время редактирования?
☐ Что если два игрока одновременно двигают токен?
☐ Что если дайс-ролл с отрицательным модификатором?
☐ Что если canvas переключили во время drag&drop?
☐ Что если имя сущности уже занято?
☐ Что если .md файл вручную отредактирован с ошибкой YAML?
```

## 7.1 BUG INTAKE И BATCHING

Когда пользователь сообщает о баге, это сначала входящий сигнал, а не автоматический приказ немедленно менять код.

### Алгоритм

1. Запиши баг в `.pi/BUG_BACKLOG.md`.
2. Добавь чекбокс в `.pi/DEVELOPMENT_PLAN.md`, если баг влияет на текущий roadmap.
3. Назначь приоритет:
   - `P0`: потеря данных, не запускается приложение, сломан save/sync.
   - `P1`: сломан основной игровой сценарий, приватность, права или мультиплеер.
   - `P2`: важная функция сломана, но есть обходной путь.
   - `P3`: мелкий UX/визуальный дефект.
4. Назначь batch key по модулю: `Canvas selection`, `Roll Engine`, `Entity CRUD`, `Permissions`, `GM Workbench`.
5. Чини сразу только `P0/P1` или баги, которые попадают в уже открытый рабочий модуль.
6. `P2/P3` группируй и закрывай тематическим срезом, чтобы не распылять контекст и не трогать одни файлы многократно.
7. После фикса обнови статус бага, план, QA-документ и сделай отдельный `fix: ...` commit.

### Если баг внесён агентом

Если дефект выглядит как regression от предыдущей AI-правки, добавь к обычному bugfix ещё один маленький шаг обучения проекта:

1. Пометь баг в backlog как `agent-induced regression` или опиши, какая правка нарушила контракт.
2. Найди контракт модуля: ближайший `.pi/docs/*`, `.pi/rules/*`, skill или `code-map`.
3. Обнови этот файл коротким правилом предотвращения: что нельзя повторять, какой API/паттерн использовать, где проверять.
4. Если контракта нет, добавь минимальную заметку в `.pi/docs/code-map.md` или создай точечный `.pi/docs/<module>.md`, но не пиши большой документ ради одной строки.
5. Добавь focused test или QA-шаг, если баг можно поймать без тяжёлой ручной проверки.

Цель: каждый исправленный агентский regression должен улучшать навигацию и правила проекта, а не только исчезать из текущей ветки.

### Когда нужно уточнить

Если баг описан неоднозначно, сначала спроси, что именно ожидалось. Не превращай неясное требование в случайный фикс.

## 7.2 САМОАНАЛИЗ ДОРОГОГО ПОИСКА

Если агент тратит слишком много контекста на поиск владельца логики, это отдельный сигнал качества проекта.

Триггеры:

- 3-5 точечных `rg`/file-read проходов не нашли нужное место.
- Приходится читать большие несвязанные файлы ради одной кнопки/фичи.
- UI-название не совпадает с названием компонента, стора или документа.
- Пользовательская формулировка может означать несколько разных действий.

Действия:

- зафиксировать проблему навигации в `.pi/DEVELOPMENT_PLAN.md` или `.pi/docs/`;
- при необходимости предложить code map, переименование, разделение файла или архитектурный refactor;
- если причина в неоднозначной формулировке — сказать об этом пользователю и уточнить;
- не продолжать бесконечный поиск без плана.

## 7.3 FEATURE INTAKE И PLANNING

Когда пользователь просит новый функционал, это тоже входящий сигнал, а не повод плодить параллельную архитектуру.

### Алгоритм

1. Запиши фичу в `.pi/FEATURE_BACKLOG.md`.
2. Добавь чекбокс в `.pi/DEVELOPMENT_PLAN.md`, если фича влияет на текущий roadmap.
3. Проверь, нет ли уже существующего фундамента:
   - если фича уже частично реализована — доделывай текущий контур;
   - если запрос на самом деле описывает сломанную существующую функцию — добавь/свяжи баг в `.pi/BUG_BACKLOG.md`;
   - если нужна новая система — оформи mini-PRD и acceptance criteria.
4. Назначь приоритет:
   - `F0`: schema/data migration, фундаментальная адресация, sync/permissions/file-system контракт;
   - `F1`: core workflow сессии;
   - `F2`: productivity/QoL или важное расширение;
   - `F3`: polish/experiment.
5. Назначь batch key по модулю: `Canvas history`, `Asset Browser`, `Entity ID Links`, `Audio Workbench`, `UI Design System`.
6. Для `F0` и функций, затрагивающих `.md`, Yjs, permissions, файловую систему или будущую desktop/Steam упаковку, сначала создай короткий design-doc в `.pi/docs/`.
7. Разбей реализацию на вертикальные срезы и закрой самый тонкий работающий срез первым.
8. После завершения обнови feature backlog, план, QA-документ и сделай отдельный `feat: ...` или `refactor: ...` commit.

### Когда нужно уточнить

Если пользователь мог ошибиться, смешал баг и фичу, или в запросе есть несколько несовместимых вариантов реализации, сначала назови развилку и уточни. Особенно это касается схемы Entity ID, ссылок, файловой системы, прав доступа и платформенной упаковки.

## 7.4 ARCHITECTURE/PRODUCT GATE

Для крупных изменений действует отдельный gate, даже если владелец пишет `продолжай`.

Gate обязателен, если фича затрагивает:
- глобальное место UI и главный workflow;
- модульную систему, plugin/mod architecture или отключаемые модули;
- роли, права, identity игроков, приватность;
- Yjs/session sync, `.md` формат, file-system contract;
- внешние API и сервисы;
- Tauri/Rust/Steam/3D или технологический фундамент.

Алгоритм:

1. Записать фичу/баг в backlog.
2. Создать или обновить design-doc с mini-PRD, вариантами, рисками и acceptance criteria.
3. Если есть зрелые аналоги или внешние API, проверить актуальные официальные источники и зафиксировать ссылки.
4. Подготовить владельцу короткий список вариантов и вопросов.
5. До одобрения делать только обратимые foundation-first срезы: сервисы, типы, тесты, удаление ошибочного UI-размещения, багфиксы.
6. Не добавлять зависимости и не закреплять финальную архитектурную развилку без явного OK.

Пример: аудио-плеер. Можно вынести звук из вкладки `Файлы`, оставить общий `audioPlayback` service и проверить bugfix playback lifecycle. Нельзя молча решить, что плеер живёт во вкладке базы, что YouTube реализуется конкретным способом, или что модульная система устроена как plugin marketplace.

## 8. ШАГ 6: ТЕСТЫ

### Что тестируем всегда:
```typescript
// 1. Чистые функции (utils)
describe('diceParser', () => { ... });
describe('entitySerializer', () => { ... });

// 2. Хуки
describe('useCalculatedStat', () => { ... });

// 3. Сторы
describe('windowStore', () => { ... });
```

### Что тестируем иногда (сложные интеграции):
- Компоненты (React Testing Library)
- API endpoints (supertest)

### Формат тестов:
- Рядом с файлом: `diceParser.test.ts`
- Или в `__tests__/` папке

## 10. ШАГ 8: GIT-ФИКСАЦИЯ

После новой фичи, ручного дебага или проверенного исправления нужно сделать отдельный осмысленный commit.

Правило:

1. Не коммить непроверенный код.
2. Перед commit прогнать релевантные проверки: `lint`, `build`, focused tests, server `tsc` если затронут сервер.
3. Один commit = один законченный срез или один понятный maintenance-срез.
4. Сообщение commit должно объяснять тип работы:
   - `feat: ...` — новая фича;
   - `fix: ...` — исправление бага;
   - `docs: ...` — документация/план;
   - `test: ...` — тесты;
   - `chore: ...` — инфраструктура/гигиена;
   - `refactor: ...` — изменение структуры без смены поведения.
5. Не смешивать unrelated test-world изменения, временные файлы и рабочий код без причины.
6. Если нужна ручная проверка владельцем проекта, commit можно делать после автоматических проверок, но в сообщении/финале отметить: `manual QA pending`.
7. Если commit/push невозможен из-за внешних ограничений, лимитов, sandbox, авторизации или недоступного origin, это не отменяет завершённый срез и не останавливает дальнейшую разработку. Нужно записать, что git фиксация отложена, и продолжать следующий безопасный срез.

Цель: git должен оставаться читаемой историей разработки, а не мусорной корзиной после длинной агентной сессии.


## 12. ЗАПРЕТЫ

```
❌ Не делай больше одного слайса за раз без подтверждения
❌ Не меняй архитектуру без обсуждения
❌ Не добавляй зависимости без явного OK
❌ Не игнорируй мультиплеер (всегда думай: а что если два клиента?)
❌ Не удаляй существующий функционал без ConfirmDialog
❌ Не оставляй console.log в production-коде
❌ Не хардкодь строки — используй i18n
❌ Не оставляй рабочее дерево грязным после завершённого проверенного среза без объяснения
```
