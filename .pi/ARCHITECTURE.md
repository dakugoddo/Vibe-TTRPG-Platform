# Vibe TTRPG Platform: архитектурный канон

> Дата: 2026-05-21
> Назначение: короткая рабочая архитектура для дальнейшей разработки.

## 1. Entity как основной контракт

Все игровые и справочные объекты описываются через `Entity`.

Минимальный контракт:

```ts
interface Entity {
  id: string;
  parentId: string | null;
  schemaVersion?: number;
  type: EntityType;
  name: string;
  description: string;
  imageId?: string;
  icon_url?: string;
  properties: Record<string, unknown>;
  tags: string[];
  database?: DatabaseType;
}
```

Сущность имеет явную версию схемы. Версия нужна не для жесткого ограничения механик, а для безопасных миграций:

- старые `.md` файлы должны открываться;
- новые блоки должны понимать отсутствие новых полей;
- миграции должны быть явными и обратимыми настолько, насколько это возможно.

Текущий путь: `schemaVersion` хранится как top-level поле Entity и пишется в YAML frontmatter. Старые файлы без версии считаются совместимыми с текущей схемой. Подробности: `.pi/docs/entity-schema.md`.

## 2. Слои синхронизации

### Persistent state

Данные, которые должны сохраняться в файлы:

- сущности и их свойства;
- canvas-элементы;
- fog of war;
- связи, порталы, теги;
- чат, если принято хранить историю сессии.

Этот слой может идти через Yjs и сохраняться с debounce в `.md` / world files.

### Ephemeral state

Временные данные, которые нужны только во время живого действия:

- промежуточные drag-позиции;
- previews рисования;
- live-resize окон;
- временные hover/selection состояния, если они не должны сохраняться.

Этот слой не должен раздувать CRDT-документы. Для него нужен отдельный WebSocket/event канал.

Текущий audio MVP использует тонкий session-command слой поверх глобального Yjs doc: хранится только последняя `AudioSessionCommand` (`play/stop`, `assetId`, `assetPath`, `volume`, `startedAt`). Команда не зеркалится в `.md`, старые SFX-команды игнорируются по TTL, а player-клиент воспроизводит её только после ручного opt-in `Звук сессии`. Если аудио вырастет в полноценный микшер/плейлисты, этот слой нужно отделить от persistent Entity data так же строго, как awareness.

### Awareness state

Данные присутствия:

- курсоры игроков;
- пинги;
- имена, цвета, роли;
- состояние "смотрит сюда".

Это awareness Yjs/WebSocket слой, а не persistent data.

## 3. Roll Engine

Roll Engine - единая точка для всех бросков.

Обязательные свойства:

- UI-компоненты не должны сами генерировать случайные числа;
- формат результата должен быть единым для чата, истории и будущих окон;
- источник случайности должен быть заменяемым;
- локальный источник по умолчанию должен использовать `crypto.getRandomValues`, если он доступен;
- будущий random.org provider подключается через тот же интерфейс, без переписывания чарлистов.

Минимальный интерфейс:

```ts
interface RandomProvider {
  id: string;
  label: string;
  nextInt(minInclusive: number, maxInclusive: number): number;
}
```

Если random.org будет асинхронным, Roll Engine нужно расширить до async API. До этого UI должен зависеть от фасада движка, а не от конкретной реализации.

Текущий фасад уже включает `rollExpression`/`resolveRollExpression`: Markdown `!roll`, будущие атаки, способности, предметные эффекты и статусы должны передавать формулу и resolver переменных в Roll Engine, а не держать собственный парсер бросков в UI.

## 4. Механики игровой системы

Полную игровую систему нужно проектировать отдельно вместе с владельцем проекта. До этого код должен поддерживать тестовые механики, но не цементировать их как единственный путь.

Правило:

- навыки и компетенции можно использовать как рабочий vertical slice;
- способности, атаки, статусы, ресурсы и предметные эффекты должны развиваться через Entity-блоки и Roll Engine;
- формулы и условия должны идти в сторону конфигурируемого Rules/Mechanics Engine, а не набора hardcoded проверок в UI.

Текущий UI-контур:

- `SkillsBlock` и `CompetenciesBlock` проверяют броски через Roll Engine;
- `AbilitiesBlock` хранит дочерние ability-сущности и бросает `diceFormula`/legacy `dice` через Roll Engine;
- `ResourcesBlock` хранит гибкие счетчики в `properties.resources`, без механических выводов;
- статусный контур живет в `AttributeBlock` через status-теги;
- `ObjectSheet` и `AttackSheet` остаются текущим контуром предметов и атак.

## 5. Права доступа

Права должны проверяться в одном месте, а UI только отражает результат:

- GM может видеть и менять все;
- player может менять свою user-базу и разрешенные сущности;
- gm-база скрыта от игроков;
- spectator/read-only режим не должен иметь путей записи.

Любая новая запись в Yjs или файловую модель должна проходить через общий permission helper.

## 6. Canvas performance

Canvas должен масштабироваться до больших карт и длинных сессий.

Запрещено без отдельной проверки:

- добавлять новые Konva layers ради удобства;
- менять world/screen coordinate contract;
- переносить частые drag/previews в persistent CRDT;
- добавлять тяжелые эффекты, которые перерисовываются на каждый mousemove.

Приоритетные оптимизации:

- keep persistent state small;
- separate ephemeral transport;
- batchDraw для тяжелых слоев;
- мемоизация derived canvas state;
- проверка canvas через реальные desktop/mobile viewports.

## 7. Документация

Канонические документы:

- `.pi/PRODUCT_VISION.md` - что строим;
- `.pi/ARCHITECTURE.md` - как строим;
- `.pi/DEVELOPMENT_PLAN.md` - текущий порядок работ;
- `.pi/planning/IDEAS.md` - идеи, критическая оценка, статусы и зависимости;
- `.pi/planning/BUGS.md` - активные баги и обязательная QA;
- `.pi/planning/QUESTIONS.md` - решения, которые нельзя принимать без владельца;
- `.pi/planning/NEXT_RELEASE.md` - только завершённые изменения следующего релиза;
- `.pi/docs/code-map.md` - владельцы логики и стартовые файлы для типовых задач.
- `.pi/docs/platform-runtime-decision.md` - runtime/Steam/3D decision draft.

Исторические документы остаются полезными, но новые агенты должны начинать с канонических файлов и `AGENTS.md`.

## 8. Bug intake и дорогой поиск

Баги сначала попадают в `.pi/planning/BUGS.md` с приоритетом, пользовательским сценарием и критерием проверки. `P0/P1` чинятся сразу, `P2/P3` группируются по модулю, если нет причины повышать срочность.

Если агент за 3-5 точечных поисковых проходов не находит владельца логики, это считается сигналом архитектурной навигационной проблемы. Нужно обновить `.pi` code-map/architecture/design документы или предложить локальный refactor, а не продолжать слепо читать большие куски кода.
